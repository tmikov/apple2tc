# Splitting system2-inc.h Implementation Plan

**Goal:** Let a program built on the `--irc1` engine have more than one translation unit. Today `system2-inc.h` *defines* the emulated machine, so every program is one file — which is why `snake-byte.c` is 5,322 lines with the Apple II ROM welded into it.

**Architecture:** Split into a declarations header and an implementation fragment. State becomes `extern`; the trivial accessors stay in the header as `static inline`, so nothing at a call site gets slower; everything substantial moves to the fragment. `system2-inc.h` survives as a two-line shim, so today's single-TU users compile unchanged.

**Tech Stack:** C11, CMake + Ninja.

## The three files

| | |
| --- | --- |
| `include/apple2tc/system2.h` | declarations: `extern` state, `static inline` accessors, the `CYCLES` macros, prototypes |
| `include/apple2tc/system2-impl.inc` | definitions: the state's storage and every non-inline function |
| `include/apple2tc/system2-inc.h` | the shim — `#include` of the two above, in that order |

`system2-impl.inc` **does not include `system2.h` itself.** It is a fragment,
not a standalone unit, so whoever includes it includes the header first. That
is what makes the shim's body and a separate-compilation `.c` the same two
lines:

```c
#include "apple2tc/system2.h"
#include "apple2tc/system2-impl.inc"
```

A program that wants more than one translation unit writes exactly that into
its own small `.c`, adds it to its target, and every other TU includes only
`system2.h`. No library, and nothing with a `.c` extension under `include/`.

## Global Constraints

- **`system-inc.h` is not touched.** Its four users are single generated files
  (`robotron.c`, `bolo.c`, `rom.c`, `as-generated/snake-byte-simple-c.c`), none
  of which wants a second TU, and it has no `emulated_entry_point` hook. If a
  later step forces a change to a *shared* interface, that would be a small edit
  there — never a split.
- Every task ends with: full `ninja -C cmake-build-debug` (93 targets, 0 errors),
  `tests/run-tests.sh`, and all three gates — snake-byte `probe-acceptance.sh`
  (31 PASS), snake-byte `verify.sh` (4 PASS), rom `probe-acceptance.sh` (2 PASS).
- Generated files under `decoded/snake-byte/reference/` are regenerated by
  `scripts/decompile.sh`, never hand-edited. The gate's `[regen]` check runs first
  and enforces this.
- `decoded/snake-byte/snake-byte.c` is hand-owned. Use
  `scripts/codegen-fingerprint.sh` to show when a change to it emitted identical
  code.

## What goes where, and why

**Stays in `system2.h` as `static inline`** — every accessor, because each is one
to three lines over the machine's state: `peek`, `poke`, `peek_zpg`, `poke_zpg`,
`peek16`, `peek16_zpg`, `peek16al`, `push8`, `pop8`, `push16`, `pop16`,
`ram_poke_impl`. Bodies do not change; only the storage they read becomes
`extern`. Each TU gets its own copy of the code and they all share one machine.

Measured beforehand so nobody re-litigates it: forcing those eleven out of line
in the reference build moved a 40,000-frame run from 2.50/2.48/2.48 s to
2.51/2.51/2.47 s. That is *not* the reason to keep them inline — they are
accessors, that is the reason. It is the reason not to agonise about the rest.

**Moves to `system2-impl.inc`** — `adc_decimal` and `sbc_decimal` (~23 lines
each), `cycles_expired`, `emulated_thread`, `run_emulated`, `shutdown_emulated`,
`engine_stop_reason`, `engine_parse_arg`, `engine_print_help`, and the ABI
wrappers `ram_peek`, `ram_poke`, `ram_peek16`, `ram_peek16al`, `get_regs`,
`set_regs`, `reset_regs`, `get_cycles`, `get_ram`. Those last nine are declared
in `a2engine.h` and called by the host by name, so they need external linkage and
cannot be `static inline` — but the header already shows the pattern: `ram_poke`
is a one-line wrapper over the inline `ram_poke_impl`.

**Stays a macro** — `CYCLES` and `CYCLES_EDGE`. `CYCLES` expands to a reference
to `branchTarget`, a *local* variable in generated code, so it can never become a
function.

### Task 1: `emulated_entry_point` gains external linkage

**Files:** `include/apple2tc/system2-inc.h`, `tools/apple2tc/IRC1.cpp`,
`decoded/snake-byte/snake-byte.c`, and by regeneration everything in
`decoded/snake-byte/reference/`.

This is the one interface change the split forces, and it is a prerequisite:
`emulated_thread` calls `emulated_entry_point`, so once the former lives in
another TU the latter cannot be `static`. Doing it alone keeps the only change
to generated output out of the larger diff.

## What this unlocks, and is not doing

Splitting the Apple II ROM routines out of `snake-byte.c` — 682 lines, 12% of
the file, a clean layer whose only upward call is `game_cout_hook` — becomes a
normal `.c` beside `system2-impl.c` instead of a textual include. Separate plan.

## Risks

- **Duplicate definitions** if a program both includes the shim and compiles its
  own impl `.c`. The linker says so loudly; there is no silent form.
- **A missed initialiser.** `s_status_not_z = 1` is the one that is not zero.
  The gates would catch it, but read the diff.
- **Regeneration drift** in Task 1: if `decompile.sh` rewrites more than the one
  word, stop and find out why before committing.
