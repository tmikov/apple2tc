`a2host_reboot()`'s own comment says it "brings the machine back up as if the
process had just started," but it deliberately does not clear RAM. Real
hardware power-on leaves RAM in an indeterminate state and the ROM's RESET
handler takes the cold path unconditionally; `a2host_reboot()` leaves the
previous session's RAM exactly as it was, so the ROM's own warm-vs-cold check
(the signature it looks for in low memory) finds a plausible warm-start and
takes that path instead. A second `boot` is a soft reset into whatever the
first session left behind, not a fresh machine.

## What's wrong

Two ways this shows, from smallest to worst:

- **Bare ROM boot** (`boot()` with no `disk1`/`rom`/`binary`): a second `boot`
  skips the cold-boot self-test/banner the first one showed. Measured with
  `a2mcp`: `boot; run(frames); boot; run(frames)` with identical inputs
  produces a different `--hash-frames=` hash from frame 0 (`caebd377...` vs
  `5a8f629d...` in one run), and the reported cycle count after an identical
  number of frames drifts by a few cycles (664950 vs 664953 over 40 frames in
  another). Nothing about the *displayed screen* is reproducible across a
  reboot, only the frame/cycle counters and whatever a front end explicitly
  reloads (a2mcp's `--key-file=` cursor, for instance).

- **Disk boot** (`boot(disk1: "dsk/Neptune.dsk")`): a second `boot` with the
  same disk does not redo the boot sequence at all. Measured: `boot(disk1);
  run(1200); boot(disk1); run(1200)` -- the first 1200 frames show the game
  actively animating (a constantly-changing video hash all the way to frame
  1200), the second 1200 frames land on a static screen reading "HIT RETURN
  TO JUMP TO THE NEXT COMMAND" that never changes again for the rest of the
  window. That message is not from a fresh $C600 disk boot; it reads like
  whatever the game itself left resident as a soft-reset handler (a common
  Apple II copy-protection trick), reached because the CPU reset vector in
  RAM was never restored to the ROM's own. The two runs' video never
  converge -- not even approximately -- within 1200 extra frames.

This is not new or specific to `a2mcp`: `a2host_reboot()` is the only caller
of the reset path outside process startup, so nothing else exercises this,
but the fidelity gap is in the shared host, not in any one front end.

## Already cost a session once

`docs/a2mcp-playing.md`'s "`boot` does not clear RAM" section exists because
an earlier session, driving Neptune, read a previous session's leftover text
as a live BASIC prompt after a boot and wrote "the disk does not autoboot"
into two documents before the mistake was caught. This issue is the second
time the same root cause (RAM survives a reboot, so old and new session state
can look alike) has misled someone -- this time into believing a `boot`
right after another `boot` reproduces a fresh start closely enough to
byte-compare video against, which for a disk session it does not do even
loosely.

## Wanted

Not fixing this now -- real power-on RAM state is not something worth
reproducing byte-for-byte, and the two documented workarounds (check `status`'s
video mode rather than trust a screenshot; do not assume a second `boot`
replays a disk session) are enough to work around it. Filed so the gap has a
name: if `a2host_reboot()` ever needs to support a truly fresh-feeling reboot
(clearing RAM, or resetting whatever signature the ROM's warm-start check
reads), this is the record of why and the two measurements that pin it down.
