`a2_io_poke()` calls `a2_io_peek()` twice for every write, both times with the
same `cycles`:

```c
void a2_io_poke(a2_iostate_t *io, uint16_t addr, uint8_t value, unsigned cycles) {
  ...
  a2_io_peek(io, addr, cycles);
  a2_io_peek(io, addr, cycles);
}
```

For `$C030` that is fatal. `a2_sound_spkr()` emits samples up to `cycle` at the
current level and then inverts the level, so the second call emits nothing --
`last_generated_cycle` has already reached `cycle` -- and inverts straight back.
The speaker level never changes, the output is a DC constant, and a program that
drives the speaker with `STA $C030` is silent.

Measured against a clean build of master, 200 speaker accesses at ~1 kHz, each
case starting from a fresh `a2_sound_t`:

```
LDA (peek) $C030 x200: callbacks=200  waveform edges=184
STA (poke) $C030 x200: callbacks=400  waveform edges=0
```

That is why `dsk/Neptune.dsk` has no sound. It drives the speaker almost
entirely with writes -- 18,163 `STA $C030` against 192 reads in a 100-second
run:

```
a2run --disk1=dsk/Neptune.dsk --headless --frames=6000 --no-sound
```

The same doubling makes `STA $C010` pop two entries off the keyboard queue
instead of one, so a burst of type-ahead loses every second key. Every other
soft switch a2io implements is idempotent, which is why nothing else shows it.

Where it came from: `EmuApple2::ioPoke` in 2021, whose comment said "According
to the Apple II Reference Manual, a write is preceeded by a read." dab2a7f moved
the body into a2io and dropped the comment with it. The claim is about the 6502
addressing modes that perform a dummy read -- `abs,X`, `abs,Y`, `(zp),Y` and the
read-modify-write instructions -- not about `STA abs`, which is what `STA $C030`
is. Even for the modes that do read first, the two bus cycles are one cycle
apart, so the pulse has width; here both carry the same stamp and cancel
exactly.

Wanted: one access per write.

Whether the dummy read of the indexed and RMW modes is worth modelling at all is
a separate question. If it is, it belongs in the CPU emulator, which is the only
place that knows which cycle the dummy read lands on -- doing it in `a2_io_poke`
cannot know, and a zero-width pulse is worse than none.
