`apple2tc --simple-c` can emit C that does not compile. Reproduced on
`decoded/neptune/testdata/neptune.b33`, at `$3802`:

    3800: A2 02       LDX  #$02
    3802: B5 B0       LDA  $B0,X      <- operand byte is self-modified
    3804: 95 04       STA  $04,X

emits

    /* $3802 LDA */ s_a = update_nz(peek_zpg((uint8_t)(ram_peek(0x3);

which is truncated mid-expression. gcc:

    error: expected ')' before ';' token

## Cause

`Disas::simpleCRead()` (tools/apple2tc/PrintSimpleC.cpp:488) returns a
`std::string` but builds it through a fixed `char buf[32]`:

    std::string Disas::simpleCRead(CPUInst inst) const {
      char buf[32];
      ...
      snprintf(buf, sizeof(buf), "peek_zpg(%s)", simpleCAddr(inst).c_str());

For a self-modified `Zpg_X` operand `simpleCAddr()` correctly returns

    (uint8_t)(ram_peek(0x3803) + s_x)

which is 33 characters. Wrapped in `peek_zpg(...)` that is 42, and
`snprintf` silently truncates it to 31 plus a NUL. `simpleCAddr()` itself is
fine -- its own buffer is 64 -- so this is purely the caller's.

The truncation is silent, so the failure surfaces as a compile error in
generated code a long way from the cause.

## Scope

It needs an operand whose byte is self-modified *and* an addressing mode whose
self-modified spelling is long. `Zpg_X` and `Zpg_Y` reach 42 characters through
`peek_zpg(...)`; `Abs_X`/`Abs_Y` reach 38 through `peek(...)`, which also does
not fit. Games without self-modifying operands never hit it, which is
presumably why it has survived -- snake-byte's `--simple-c` output builds.

## Fix

Build the string with `std::string` concatenation instead of a buffer, so the
length cannot be exceeded at all:

    return "peek_zpg(" + simpleCAddr(inst) + ")";

Bumping the buffer would work today and rot the next time an addressing mode's
spelling grows.

    Correction to the Scope section above: only `Zpg_X` and `Zpg_Y` overflow.
    `Abs_X`/`Abs_Y` do not, and the "38 characters" figure was wrong.

    Counted rather than estimated:

      peek(ram_peek16(0x3803) + s_x)              30 chars  -> fits in buf[32]
      peek_zpg((uint8_t)(ram_peek(0x3803) + s_x)) 43 chars  -> truncates at 31

    So the trigger is narrower than first written: a self-modified operand in
    zero-page indexed addressing specifically, because that mode is the only one
    whose self-modified spelling adds the `(uint8_t)(...)` wrapper on top of the
    `ram_peek(...)`.

    This also explains why snake-byte never hit it. Its `--simple-c` output has
    exactly one self-modified indexed operand and it is the `peek(ram_peek16(...))`
    form, which fits, so the committed as-generated file has no unbalanced lines
    and builds. Regenerating snake-byte with the fix changes nothing about that
    site.
