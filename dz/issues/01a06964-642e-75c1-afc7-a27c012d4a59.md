`s_script_ptr` is a `uint16_t` holding an address in the emulated RAM array,
walked a byte at a time through `peek()`. `seek_script` starts it at a bare
`0x8000`.

The display lists are static, read-only data that arrive with the game image
and never change. The address exists because the 6502 kept this pointer in two
zero-page bytes at `$000A`, not because anything in the C needs it.

What it costs:

- **No type.** The scripts are undifferentiated bytes at an offset. There is no
  array of scripts and nothing a reader can look at to learn the shape, so the
  shape is re-explained in prose at five sites (snake-byte.c:202, :954, :1166,
  :3615, :3616), each of which cites `$8000` because the code has no word for
  the place.
- **No bounds.** Walking past the last script reads whatever is next in memory
  and returns it as an opcode. Only the terminator bytes prevent it.
- **`peek()` per byte**, so a walk over constant data is a call into the RAM
  array rather than a pointer increment.
- **Pins the data to `$8000`.** The image must stay resident at exactly that
  address for the lists to be readable.

It is also what produced the fossil fixed in 6779986: a 16-bit *number* can
wrap, so `game_next_byte` carried an empty branch testing for it. A pointer
into a sized array cannot, and the question never arises.

Wanted: the scripts as typed, named, read-only data -- an array of scripts, or
a `const uint8_t *` into the image -- with the base address named once.

Scope caveat, and the reason this is not a fix to `seek_script`: the file
reaches through `s_ram` for a great deal besides this. Moving one pointer out
is the first step of a direction, not a tidy-up. The scripts being read-only
means no oracle depends on them living in RAM, so it can be done alone -- but
it should be done as its own piece of work.
