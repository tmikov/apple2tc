`decoded/robotron` calls the ROM's `PREAD` (`JSR $FB1E`) at `robotron.c:744`
and `:794`. The decompiled routine at `robotron.c:13511`-`13525` splits the
timing loop across two basic blocks and charges each up front:

```c
    case 0xfb25: // [$FB25..$FB29]    5 bytes
      CYCLES(0xfb25, 9);
      /* $FB25 LDA */ s_a = update_nz(peek(0xc064 + s_x));
      /* $FB28 BPL */ ...
    case 0xfb2a: // [$FB2A..$FB2C]    3 bytes
      CYCLES(0xfb2a, 6);
      /* $FB2A INY */ s_y = update_nz(s_y + 1);
      /* $FB2B BNE */ ...
```

That is 15 cycles per iteration. The hardware loop is 11: `LDA abs,X` 4,
`BPL` not taken 2, `INY` 2, `BNE` taken 3 -- the figure `PREAD` is calibrated
against, and the same 11 Neptune's hand-rolled loop uses.

## Why it is invisible today

`$C064` is not emulated and reads 0, so bit 7 is never set, the loop exits on
its first pass, and the count is 0 whatever an iteration costs. Nothing
observes the discrepancy.

It becomes observable the moment the game port lands (dz
`01a074d9-9034-72fe-9efe-87de198c6dd6`). Against a device calibrated to the
hardware's 11 cycles per count, a centred paddle -- position 127, a one-shot
of `11 * 127 + OFFSET` cycles -- is sampled every 15 emulated cycles instead
of every 11, so Robotron counts roughly `1402 / 15` and reads about **93**
where the interpreter reads 127.

## Not a game-port bug

This is the generated code's cycle accounting, not the device. Two properties
of the accounting produce it: cycles are charged per basic block rather than
per instruction, and they are charged *before* the block's IO access runs
(`lib/cpuemu/emu6502.cpp:151`). Any decompiled program that times a loop
against an IO one-shot is exposed to the same error; Robotron is simply the
one in the tree that does it.

Note the calibration test proposed in
`docs/superpowers/specs/2026-09-07-game-port-paddles-design.md` cannot catch
this. It runs the real ROM `PREAD` under `a2run`, whose accounting is per
instruction and correct. Only the decompiled build is wrong, so any check has
to run the generated C.

## Wanted

A decision, then the work that follows from it: either make block cycle
accounting exact enough that a timing loop reads the same count as the
interpreter, or state that decompiled programs do not reproduce IO timing
loops and say what that costs. The spec above accepts the ~93 as a limitation
so it is not mistaken for a regression when the port lands; that acceptance is
a placeholder for this issue, not a resolution of it.
