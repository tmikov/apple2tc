While a `--key-file=` recording is loaded, a2emu's display function keys
(F3/F4/F5/F6) are dead. Hit while watching a replay -- the exact case those
keys exist for.

## What's wrong

`event_cb()` in `lib/a2host/a2host_gui.c` guards on
`a2host_key_replay_active()`:

```c
// A cycle-stamped recording is driving input; real keystrokes must not
// perturb it.
if (a2host_key_replay_active())
  return;
```

and returns before ever reaching the `SAPP_EVENTTYPE_KEY_DOWN` switch further
down, where F3 (hi-res render mode), F4 (persistence toggle) and F5/F6
(persistence decay) are handled. `a2host_key_replay_active()` is
`key_presses_ != NULL`, and that list is freed only once the recording is
exhausted -- so the keys come back to life at the end of the replay, having
done nothing for its entire length.

The guard itself is correct and earns its keep: a live keystroke reaching the
*emulated machine* would perturb a cycle-stamped recording, which is the whole
point of having it. But F3-F6 never reach the machine -- none of their cases
calls `a2host_press_key()`. They only change how this front end draws the
screen. The machine cannot tell A2_HGR_COLOR from A2_HGR_MONO140, or whether
persistence is on, because nothing about how the display is decoded is
observable from inside the emulation. Blocking them buys the guard nothing
and costs the person watching a replay everything F3-F6 are for.

F1/F2 (a2emu's bundled-game keys, `event_hook_`) already get first refusal
*above* this guard, so a host-owned key running ahead of it is the established
shape here -- F3-F6 sitting below it looks like an oversight rather than a
policy.

## Wanted

Let F3/F4/F5/F6 through regardless of `a2host_key_replay_active()`, while
every key that reaches the machine (the `SAPP_EVENTTYPE_CHAR` branch and the
DELETE/BACKSPACE/LEFT/RIGHT/ENTER/ESCAPE cases, all of which call
`a2host_press_key()`) stays exactly as blocked as it is today.
