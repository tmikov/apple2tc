Play `dsk/Neptune.dsk`, steer for a while, press one key the game does not use,
and the keyboard is dead for the rest of the session. Reported from the windowed
build; it reproduces headless.

## What the game does

Neptune steers with I/J/K/M. Its handler, disassembled out of a snapshot taken
at `$1060` during play:

```
1060: AD 00 C0  LDA $C000
1063: 10 49     BPL $10AE     ; no key -- leave, without touching the strobe
1065: C9 CD     CMP #$CD      ; 'M'  -> $E3++
1077: C9 C9     CMP #$C9      ; 'I'  -> $E3--
1089: C9 CB     CMP #$CB      ; 'K'  -> $E4++
109B: C9 CA     CMP #$CA      ; 'J'  -> $E4--
109D: D0 0F     BNE $10AE     ; anything else -- leave, WITHOUT strobing
...
10AB: 8D 10 C0  STA $C010     ; reached only on I, J, K or M
10AE: 4C 80 11  JMP $1180
```

`STA $C010` sits on the recognised-key path only. Two more sites do the same
thing with their own keys -- `$138C` for 'A' and `$1300` for 'Z' -- each
strobing only when its own key matched. (All three are patched in and out by
`$35A2`/`$3736`, which is how the game switches between keyboard and joystick
control; a keypress selects the keyboard, and that is also what starts the game
from the title screen.)

This is a standard idiom, and on real hardware it is harmless. The Apple II
keyboard is a **single latch**: the encoder writes the new keycode into it and
asserts the strobe on every keypress, whether or not the program acknowledged
the previous one. An unrecognised key sits in the latch doing nothing until the
next key overwrites it.

## What a2io does

`lib/a2io/a2io.c` models the keyboard as a **FIFO**, and the only thing that
removes its head is `KBDSTRB`:

```c
static uint8_t kbd(a2_iostate_t *io) {
  return io->keys_count == 0 ? io->last_key : io->keys[io->keys_head] | 0x80;
}
```

So against a program that reads `$C000` without strobing, the head never leaves.
Every later key queues behind a key the program will never acknowledge, and none
of them is ever visible. The windowed build makes it worse rather than better:
`event_cb` in `lib/a2host/a2host_gui.c` calls `a2host_push_key_if_empty()`,
which refuses to enqueue at all while anything is pending, so a later keypress
is dropped at the door.

## Reproduction

`--key-file` of eight keys -- one to start the game, three `J`, one `Q`, three
more `J` -- and a probe on `$1063`, where A holds whatever the latch returned,
printing it beside the two steering variables:

```
probe kb(kv = a, e3 = peek8($E3), e4 = peek8($E4)) {
  printf("kv=%02X e3=%02X e4=%02X\n", kv, e3, e4)
}
install kb at $1063
```

```
a2run --disk1=dsk/Neptune.dsk --headless --frames=2200 --no-sound \
      --key-file=repro.keys --probe=kb.probe --probe-out=kb.out
```

Every state change in the resulting 552 lines:

```
  1: kv=4A e3=00 e4=00
248: kv=CA e3=00 e4=00     <- 'J' seen, strobed
249: kv=4A e3=00 e4=FF     <- steered left
269: kv=CA e3=00 e4=FF     <- 'J' seen, strobed
291: kv=CA e3=00 e4=FF     <- 'J' seen, strobed
312: kv=D1 e3=00 e4=FF     <- 'Q'
```

`kv=D1` is the last state change in the run. For the remaining 241 polls the
latch reads `$D1`, and the three `J` presses stamped after it are never seen.

## Wanted

The hardware side modelled as what it is: one latch plus one strobe flag, where
a new key overwrites the latch and re-asserts the strobe regardless of whether
the previous key was acknowledged.

The queue cannot simply be deleted -- it is what keeps scripted input from being
lost -- but the two things it currently conflates come apart cleanly:

- **Untimed text** (`--kbd-file`, `a2host_buffer_keys`) is a string to be typed
  into a program at whatever rate that program reads. It wants type-ahead:
  staged, and handed to the latch as the program consumes it. That is what the
  queue is for, and `drain_kbd_file`'s `key_room()` pacing already assumes it.
- **A real keypress, and a cycle-stamped replay** (`--key-file`, a probe's
  `key`), are hardware events at a moment in time. They want the latch,
  overwritten. This is the half that is currently wrong.

`a2host_push_key_if_empty()` needs revisiting with that split: its comment
justifies itself by `--record-keys` fidelity -- "a burst typed between two probe
firings would collapse to its first key while recording and not while
replaying." Under a latch a burst collapses to its *last* key, on hardware and
in a replay alike, so the recording stays faithful without the door being shut.

Related but separate: `a2_io_poke()`'s double access makes `STA $C010` pop two
queue entries instead of one -- see the speaker issue.
